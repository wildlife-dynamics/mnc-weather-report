Troubleshooting

Common issues encountered while configuring, running, or contributing to the MNC Weather Report workflow, and how to resolve them. If your issue isn't listed here, open an issue on GitHub.

Configuration & Connections

No data / everything skipped

This workflow only reads from the EarthRanger subject group ER2ER - From GMMF — this name is hardcoded in spec.yaml and is not a configurable field anywhere in the workflow form. If your instance's weather stations are registered under a different subject group name, this workflow won't find them; every task from observation retrieval onward shares a skip-on-empty policy, so the run will complete but produce empty outputs rather than erroring.

EarthRanger connection fails or times out

Verify the server URL, username, and password configured in the Data Source Connection. Confirm you can log into that same EarthRanger instance directly in a browser with the same credentials. Credentials aren't validated at setup time, so an invalid password only surfaces as an error once the workflow actually runs.

Some charts are missing a variable / show gaps

Each of the seven variables (precipitation, surface air temperature, wind speed, wind gusts, soil temperature, relative humidity, atmospheric pressure) is extracted from the observation's JSON detail field by matching a specific key name. If a given weather station's observations don't include that key in their JSON payload, that variable comes back empty for that station — this is a per-station data issue in EarthRanger, not a workflow configuration problem.

Output & Charts

weather_summary_table.csv is empty or missing rows for a station

The daily summary is grouped by [weather_station, date]. A missing day for a station usually means there were no observations from that station on that date within your selected Time Range — widen the range and re-run to confirm.

A chart's Y-axis values look wrong (e.g. temperature far too high/low)

Check which aggregation is applied to that variable: precipitation is summed per day, wind gusts takes the daily maximum, and everything else (temperature, wind speed, soil temperature, relative humidity, atmospheric pressure) is averaged. A station reporting in different units than expected (e.g. Fahrenheit instead of Celsius) will also produce values that look "wrong" relative to the chart's labeled unit — this reflects what EarthRanger recorded, not a workflow bug.

Dashboard widgets are missing charts

The dashboard always shows all seven plot widgets (Precipitation, Temperature, Wind Speed, Wind Gusts, Soil Temperature, Relative Humidity, Atmospheric Pressure) — each widget-creation task is set to always run, even on empty data. If a widget appears blank, the underlying variable had no data for the analysis period, rather than the widget failing to render.

No outputs written / can't find results

All outputs are written to the directory specified by the ECOSCOPE_WORKFLOWS_RESULTS environment variable. Confirm it's set and points to a directory the workflow process can write to.

Contributing & CI

These apply if you're modifying the workflow itself (spec.yaml, test-cases.yaml, or the generated ecoscope-workflows-mnc-weather-report-workflow/ directory) and opening a pull request.

Generated files differ from committed files in ecoscope-workflows-mnc-weather-report-workflow

The generated workflow directory is out of sync with spec.yaml. Run the recompile script locally and commit the result:

pixi run --manifest-path pixi.toml --locked bash -c "./dev/recompile.sh --update"

Found wildcard version (*) in requirements or Found local file channel (file://) in requirements

In spec.yaml, every dependency under requirements must pin an exact version and use a remote conda channel — wildcard versions and local file:// channels are only valid for local development, not for CI using published packages.

VERSION.yaml (...) must be greater than main branch (...)

Bump MAJ/MIN/PATCH in ecoscope-workflows-mnc-weather-report-workflow/VERSION.yaml so it's strictly greater than the version on main before opening or updating a PR.

test-cases.yaml references a configure_base_maps parameter that doesn't do anything

The current test-cases.yaml includes a configure_base_maps override, but spec.yaml has no task with that ID — this workflow doesn't render any maps. It's a harmless leftover (likely copied from another workflow's test case) rather than something actively wired in; if you're cleaning up test-cases.yaml, it's safe to remove.

Workflow tests fail in CI but pass locally (or vice versa)

test.yml runs test cases against all of ubuntu-latest, macos-latest, and windows-latest. If a test only fails on CI, check whether it depends on EarthRanger credentials being available as secrets or on OS-specific path handling.
